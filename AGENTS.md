## Architecture ownership

- `blender/simulation_admission.py` owns coherent Admission Snapshot capture, preflight, Replacement Cutover, solver configuration, and admission cleanup.
- `blender/scene_bridge.py` owns only the Solver Session, direct scene synchronization/stepping, statistics, errors, teardown, and established lifecycle compatibility functions.
- `blender/output_publication.py` owns persistent output preparation/publication; `viewport_overlay.py` draws diagnostics only.
- `blender/playback.py` owns non-authoritative Preview/Cache Playback policy and playback handlers. Preserve its exact catch-up, desynchronization, status, error, and backend presentation.
- `blender/cache_bake.py` owns sequential Production Cache Bake. It bypasses Preview Playback handlers and Output Publication and writes full authoritative cache data. Do not claim bitwise CUDA repeatability: atomic accumulation, compaction/emission ordering, and derived marching-cubes output are numerically nondeterministic.
- `blender/pending_settings.py` owns the exhaustive setting lifecycle registry, Applied Settings Snapshots, pending presentation/transitions, and depsgraph/undo/load handlers. UI/property adapters must not reconstruct this policy.
- Dependency direction is adapters → deep Blender modules → Solver Settings / Output Publication / Solver Session → `sim` and `io`. Review artifacts do not certify core behavior without source/runtime evidence.

## Diagnosis scope contract

- Treat the named demo, scene, test, report, or lower-agent finding as the reproducer, not as presumed ownership of the defect. Before claiming a root cause, trace the observed path to the deepest shared owner and enumerate its production callers and sibling lanes.
- Every diagnosis must classify scope as one-off, shared-path, or unproven. A one-off claim requires evidence that the reproducer is unique and the shared path is unaffected. A shared-path claim must name affected lanes and activation conditions. Without caller tracing and a sibling or contrasting-path check, report the diagnosis as unproven.
- Do not attribute an architectural defect to the demo that exposed it. Apply this rule equally to problems reported by the Owner, users, tests, reviewers, or lower agents.
- Passing one reproducer does not close a shared-path issue. Verify the common seam and at least one affected sibling lane before claiming resolution.

## Demo playback contract

- `docs/DEMO_SCENE_CONTRACT.md` is the canonical definition of a demo. Reserve **demo** for a real, reopenable FluidSim simulation; static examples, renders, fixtures, benchmarks, and review scenes are not demos.
- Every tracked `demos/*.blend` is a playable demo, including source-workflow, cache-review, and opt-in scenes. It must contain a designated Domain object with authoritative object-owned settings, reopen at `frame_start` with live playback ready, restart from that frame, initialize a non-empty solver through its intended owned sources or seed objects, and publish visibly changing owned particle, whitewater, or surface output when advanced by the real frame handlers.
- The feature named by a demo must execute in the production runtime, not merely appear in UI state, labels, metadata, or precomputed geometry. A Custom Effects demo must have an enabled, applied scene effect, a real domain and non-empty solver, runtime effect execution during frame advancement, and dispatch/call evidence or a deterministic output difference from a disabled-effect control.
- A saved preview mesh, static before/after comparison, build-time-only solver state, external temporary cache, single preloaded frame, or generated CPU fixture does not satisfy the demo contract. Demo builders must leave no hidden foreign seed objects, stale Scene mirrors, or settings from another demo.
- Files under `fluidSim_warp_blender51/resources/examples/` are examples or validation artifacts unless separately promoted through the complete demo contract. Never open or present one as fulfillment of a demo request solely because it is a `.blend` file or contains effect-generated geometry.
- `tools/check_demo_blends.py` is the executable all-demo gate. Keep its tracked scene inventory and owned-source/seed expectations synchronized with `demos/*.blend`; verify authoritative domain ownership, reset/reopen initialization, nonzero solver state, and changing owned output through the real frame path. Add focused runtime acceptance for the capability each new demo claims.
