# FluidSim Linux and UI certification plan

Date: 2026-10-17. Status: proposed executable certification contract; no certification granted. This document plans the work needed to qualify FluidSim on Linux. It does not authorize implementation, new test runs, commits, publication, or changes to accepted policy.

All code, specification and operational evidence paths in this plan are relative to the repository root unless explicitly described as bundle-internal. The durable evidence entry point is `evidence/linux-qualification-20261017-source-round/INDEX.md`. Recovered `/workspace/shared/` and ZIP-internal locations below are archival provenance only; execution uses a complete checkout and evidence installed at that durable entry point.

## Product and platform claim

Certify the delivered FluidSim Warp 4.0 liquid extension, its real installer, artist preview/bake/cache/export workflows, Liquid Deck/Preview, rigid coupling, and the four canonical playable demos. The production boundary is `fluidSim_warp_blender51/`, installed through Blender's extension system. A source import, static scene, CPU fixture, or opening a gallery scene cannot certify playable simulation.

Current `version.py` declares Windows and Linux x64 packaging but records only Windows runtime qualification. `docs/RELEASE_4_0_ACCEPTANCE.md` deferred Linux CI and Linux USD certification to 4.1. The requested Linux work therefore needs a new Linux-qualified candidate/release record; this plan does not rewrite the historical 4.0 Windows decision. Learned pressure guess remains hidden/off, without weights, as already accepted. Archived custom-Blender/zero-copy experiments are excluded.

The first Linux profile is proposed as Debian 13.6 x86_64/glibc 2.41, official stock Blender exactly 5.2.0, Python 3.13.13 and the SHA-locked Warp 1.18.0+cu13 wheel. CUDA qualification additionally needs a declared NVIDIA GPU, VRAM, R580-series or newer compatible driver, real CUDA driver API >=13.0, and usable native viewport. Freeze the actual GPU/driver/display/scene limits before measurement. Other distributions, architectures and GPUs receive no inferred support. Blender 5.2.2 is a separate compatibility row, not a replacement for the repository's exact 5.2.0 pin.

## Verdicts, artifacts and retest rules

Each case records PASS, FAIL, BLOCKED, NOT_RUN or INCONCLUSIVE. PASS requires the exact claim's complete successful exit, explicit required markers, identity match and meaningful output. A confirmed violated expectation is FAIL. Missing required GPU/driver/original Git/predecessor is BLOCKED. An unexecuted case is NOT_RUN. Timeout, lost process, absent terminal summary, missing evidence or identity conflict is INCONCLUSIVE, never a pass. Skips stay in the denominator and cannot close mandatory GPU/output requirements. Overall Linux certification remains blocked unless every required case is PASS or a narrowly justified non-applicability has been explicitly accepted without changing product scope.

Retain: frozen contract/profile, source and dirty-file hashes, original distribution provenance/executable hashes, dependency lock and actual loaded paths, ZIP and installed member maps, all argv/cwd/environment/start/end/exit records, unedited stdout/stderr, JUnit summaries, gate manifests, raw synchronized timings, scene/input hashes, `.blend` fixtures, actual rendered/export outputs, UI captures tied to frames/actions, failure-control results, and final hash manifest. Store failed attempts separately and link superseding runs. A schema-valid receipt alone does not prove truthful execution.

Any source, package, wheel, shader, driver, Blender, fixture, tolerance or verifier change invalidates affected receipts. Preferences-only changes require focused regression plus rebuilt installed CPU/UI/lifecycle checks; final release still needs the same final artifact's full required gate. Numerical/performance changes require before/after focused tests, the full physics/demo/accuracy/performance matrix and export checks. Reuse only source-hash-bound evidence allowed by the current gate, with an explicit dependency analysis. No broad rerun merely because documentation changed.
