# Proposal: split `FLUIDSIM_PG_settings` into scene-scoped and domain-scoped groups

Status: **Phases 0 and 1 complete**; Phases 2-5 not started. Written 2026-09-10.

Phase 0's deliverable is [ownership-map.md](ownership-map.md), generated by
`tools/ownership_map.py` and pinned by `tests/test_ownership_map.py`.

## Problem

`properties.py:1728` and `properties.py:1731` bind **the same PropertyGroup class** to
two different scopes:

```python
bpy.types.Scene.fluidsim         = PointerProperty(type=FLUIDSIM_PG_settings)
bpy.types.Object.fluidsim_domain = PointerProperty(type=FLUIDSIM_PG_settings)
```

All 232 annotated fields therefore physically exist on both datablocks. Nothing but
convention says which copy is authoritative for a given field, so reading the wrong one
returns a plausible-looking stale value instead of failing.

Every one of the following exists only to re-derive, at runtime, the ownership
information that this binding discards:

| mechanism | file |
|---|---|
| `active_domain_settings()` | `blender/scene_bridge.py` |
| `schema_version` + one-way copy | `blender/migration.py` |
| `setting_owner()` / `_SCENE_OWNED_TIERS` / `_SCENE_OWNED_FIELDS` | `blender/pending_settings.py` |
| `_authoring_owner()` / `_DOMAIN_AUTHORED_SIGNATURE_FIELDS` | `blender/pending_settings.py` |
| `SCENE_OWNED_SETTINGS` | `presets/schema.py` |
| `_domain_owner()` / `owner_redirect` mirrors | `blender/ui_scene.py`, `blender/ui_physics.py` |

Defect #5 and the ~53-field "UI writes scene, solver reads domain" bug are both symptoms
of it, not independent bugs.

## Proposed end state

Two PropertyGroups, disjoint:

- `FLUIDSIM_PG_scene` on `Scene.fluidsim` — **85 fields**
- `FLUIDSIM_PG_domain` on `Object.fluidsim_domain` — **147 fields**

No field on both. A read against the wrong group raises `AttributeError` at the read
site rather than returning a stale value. `migration.py` and `schema_version` are
deleted outright; `setting_owner`, `_authoring_owner` and `SCENE_OWNED_SETTINGS` are
deleted; `active_domain_settings()` shrinks to a plain accessor with no fallback branch
and no version check.

This is a `.blend` file-format break. Acceptable — the project makes no backward
compatibility guarantee.

## Measured blast radius

All figures verified by static analysis of the current tree (`feat/ui-redesign-phases-0-3`).

| quantity | value |
|---|---|
| annotated fields on the shared class | 232 |
| already classified by the tier registry | 232 (100%, no orphans) |
| candidate scene-scoped | 85 |
| candidate domain-scoped | 147 |
| fields whose scope is **contested** (UI writes scene, consumer reads domain) | **49**, resolved by Phase 0 and repaired by Phase 1; the pre-Phase-0 estimate of 35–53 counted 25 `*_attribute_*` fields that have no UI control at all |
| `scene.fluidsim` references in the shipped add-on (non-test) | 206 across 31 files |
| files outside the add-on referencing either datablock | 72 (`tools/`, `artifacts/`, root review scripts, repo tests) |
| `getattr()` calls against a settings group | 139 |
| ...of those, passing a default | **131 (94%)** |

The tier registry already partitions all 232 fields with no unclassified remainder. That
is the single biggest de-risker: the partition does not have to be invented, only
audited and then enforced by the type system.

## The 94% problem

131 of the 139 `getattr()` reads against a settings group pass a default:

```python
profiling_enabled=bool(getattr(fs, "profiling_enabled", False))
```

After the split, that line **still returns `False`** when `fs` is the wrong group. It
does not raise. Without Phase 3 below, the split buys naming clarity and almost none of
the enforcement value that motivates it. Worst-affected files: `blender/playback.py`
(18), `blender/output_publication.py` (16), `blender/pending_settings.py` (12),
`blender/ui_scene.py` (11), `blender/geometry_nodes.py` (10).

**This is the main reason the split could fail to pay for itself.** Treat Phase 3 as
mandatory, not optional cleanup.

## Phases

Each phase is independently shippable and independently revertable.

### Phase 0 — Produce the authoritative ownership map (no code changes) — **DONE**

Deliverable: [ownership-map.md](ownership-map.md), one row per field, generated by
`tools/ownership_map.py` (AST resolution with interprocedural parameter binding, call-graph
reachability for the `owner_redirect=True` mirrors, and evaluation of the field *tables*
that drive the bulk read paths) and pinned by `tests/test_ownership_map.py`.

**Gate: passed.** All 232 fields carry exactly one declared scope, and 223 of them have
static evidence for at least one end of their data flow. The 9 without any evidence are
resolved by being provably dead (below), not by being unresolvable.

Three things the map established that a grep-based inventory would have gotten wrong:

1. **The read side is table-driven.** `solver_settings.apply_scene_settings` copies via
   `for source in DIRECT_SETTING_FIELDS: getattr(fs, source)`, so most fields have no
   per-field read site at all. Resolving them needs the table's *contents*, not its
   source text.
2. **Fields flow in two directions.** The `stat_*` block is written by the runtime
   (`scene_bridge.step`, `playback.play_cache_frame`) and *displayed* by a panel, the
   exact inverse of the authoring direction. Judging it by the authoring rule alone
   reports 21 false "unobserved" fields.
3. **The 25 `*_attribute_*` fields have no UI control whatsoever.** They appear in no
   UI module. `_authoring_owner()` declares them `scene`-authored, which describes a
   write path that does not exist; they are consumer-read-only from the domain group.
   They were previously counted among the contested fields — they are not contested.

Resolved counts (verdict definitions are in the map itself):

| finding | fields |
|---|---:|
| write lands where the consumer reads (`OK`, `OK_MULTI`) | 105 |
| **`BROKEN`** — UI writes a datablock no consumer reads | **49** |
| **`PUBLISHED_BROKEN`** — runtime writes one datablock, the panel displays the other | **1** |
| telemetry that lands correctly (`PUBLISHED`, `PUBLISHED_MULTI`) | 28 |
| consumer-read-only, no UI control | 29 |
| UI-local state | 3 |
| no resolved reader (`INTERNAL`, `UNOBSERVED`) | 16 |
| UI writes it, nothing consumes it (`export_attributes`) | 1 |

The contested set is therefore **49**, not 35–53, and the resolution is `domain` for all
of them — their consumers are `build_settings`, `gather_height_source` and
`simulation_admission`, all of which read `active_domain_settings`.

**New defect found by the map:** `height_error` (`PUBLISHED_BROKEN`).
`scene_inputs.gather_height_source` writes it to the **domain** group
(`blender/scene_inputs.py:1007`) while `ui_scene.py:264` displays
`context.scene.fluidsim.height_error`, so on a migrated scene the height-field error
message is never shown. Same root cause, opposite direction; fix it alongside Phase 1.

**16 fields have no resolved reader**, 6 of which have no reference anywhere in the
repository outside their own declaration (`playback_advanced_expanded`,
`surface_advanced_expanded`, `snippet_editor_lines`, `shortcut_field`,
`shortcut_constant_name`, `shortcut_constant_value`). Their declared scope is
unfalsifiable — the split may assign them either way. Delete them rather than migrate
them. `cache_format` is touched only by `tools/release/*`, which Phase 5 must migrate
anyway.

Naive scope estimate is misleading here: the map was the hard part, not the refactor.

### Phase 1 — Repoint the contested panels — **DONE**

15 panel `draw()` methods in `blender/ui_scene.py` and `blender/ui_physics.py` now bind
`_domain_owner(context)` instead of `context.scene.fluidsim`, so the UI writes where the
solver reads. `BROKEN` and `PUBLISHED_BROKEN` are both **0** in the regenerated map; the
49 contested fields are `OK` and `height_error` is `PUBLISHED`.

**Four fields had to move that were not in the contested 49.** `height_enabled`,
`surface_enabled` and `whitewater_enabled` each gate the very panel (or `poll`) that
draws the contested fields, and all three are read from the domain group by
`solver_settings`/`scene_inputs`. Repointing the parameters while leaving the gate on
`scene.fluidsim` would have rendered a panel that looks enabled while the solver still
sees the feature off — strictly worse than the bug being fixed.
`live_surface_publish_cadence` shares a `draw_property_grid` with three contested fields
and is itself a solver setting (`DIRECT_SETTING_FIELDS`, `sim/solver.py:535`). The
Phase 0 classifier rated all four `OK_MULTI` rather than `BROKEN` because a *second*
consumer happened to read the scene group — which understated them: their solver-side
consumer was stale exactly like the 49.

**Three panels are mixed and were split rather than repointed.** `Display`,
`Materials & Collection` and the three Physics `*_output` panels draw genuinely
scene-scoped controls (`show_*`, `whitewater_output_mode`, `whitewater_display_scale`,
the material pickers) beside domain-scoped ones. These bind both owners explicitly;
blanket-repointing them would have traded 49 broken fields for a new set.

Moving the four gates required following through on the consumer side, since those
fields are read beside scene-scoped display flags:

| file | change |
|---|---|
| `blender/output_publication.py` | new `_domain_settings()`; 5 functions read `show_*` from the scene group and `*_enabled` / `live_surface_publish_cadence` from the domain owner |
| `blender/command_line.py` | scene validation reads `height_enabled` from the domain owner |
| `blender/setup_wizard.py` | **new defect** — Quick Container seeded `height_enabled`/`height_emission_mode`/`height_base` onto `scene.fluidsim`, so the wizard produced migrated scenes whose height fill never ran |
| `blender/ui_scene.py` | `_surface_enabled()`/`_whitewater_enabled()` polls follow the toggles; `_domain_owner()` hardened for `poll` contexts with no `scene` |

**This phase changes simulation results.** Settings that were silently ignored on
migrated scenes now apply — height fields, surface reconstruction and filtering,
whitewater emission/classification/lifetime/dynamics, and profiling. Demo `.blend`
scenes, golden outputs and perf benchmark baselines will shift and need deliberate
re-baselining; the diffs are attributable to this commit alone.

`tests/test_ownership_map.py` pins `EXPECTED_BROKEN` and `EXPECTED_PUBLISHED_BROKEN` as
**empty**, guarded by `test_fault_verdicts_are_still_reachable` so the empty pins cannot
pass by the analyzer forgetting how to report a fault. It also now pins
`EXPECTED_OK_MULTI`: a panel drifting back to `scene.fluidsim` while a sibling panel
still writes the domain group scores `OK_MULTI`, not `BROKEN`, so without that pin the
most likely regression would have gone uncaught (verified by perturbation).

### Phase 2 — Split the class

Mechanical but wide: 206 references across 31 non-test files in the shipped add-on.
Behavior-neutral by construction if Phase 0 and 1 are correct; any behavior change here
is a bug.

### Phase 3 — Audit the 131 defaulted `getattr()` reads

Convert to direct attribute access wherever the field must exist on that group. Keep the
default only where absence is genuinely legitimate. Without this the split does not
enforce anything.

### Phase 4 — Delete the scaffolding

`migration.py`, `schema_version`, `setting_owner`, `_authoring_owner`,
`SCENE_OWNED_SETTINGS`, the `owner_redirect` mirror machinery, and the five ownership
tests in `tests/test_pending_settings_registry.py` that exist to pin a partition the
type system now enforces.

### Phase 5 — Non-shipped callers

72 files. Triage rather than migrate wholesale: `tools/release/validate_*_blender.py`
gate releases and must be migrated; `artifacts/live_review/probe*.py` and
`artifacts/diagnose_*.py` are historical one-off repro scripts and should be deleted or
left to rot deliberately, not carried forward.

## Risks

1. **The 94% defaulted-`getattr` problem** — mitigated only by Phase 3. Highest risk to
   the value of the whole exercise.
2. **Phase 1 changes simulation output.** Not a regression, but it will read like one in
   any comparison against existing baselines. Re-baseline deliberately.
3. **41 test files** reference the datablocks and will need updating alongside Phase 2.
4. **Blender RNA/registration** — renaming the registered PropertyGroup invalidates every
   existing `.blend`. Accepted by the no-backcompat position, but it means no gradual
   rollout: the split lands atomically for users.

## Recommended sequencing

Phase 0 first and alone — it is cheap, it is the gate, and its output is independently
valuable even if the split is never done (it is the map that would have prevented
defect #5). Decide whether to continue after reading it.

Phase 0 is done and it earned its keep before the split was even attempted: it found
`height_error`, corrected the contested-field count, and identified 16 fields to delete
rather than migrate. Phase 1 is done and found one more live defect the map had not
covered (`setup_wizard`'s height seeding, a *write* site rather than a read).

The map now reports no fault verdicts, so the remaining phases are refactors rather than
bug fixes — Phase 2 is the next step, and the 7 residual `OK_MULTI` fields are its first
concrete task: each has a consumer still reading the scene group for a domain-owned
field, which the split makes impossible by construction.
