# FluidSim Warp 1.0.252 Merge Design

## Objective

Prepare `FluidSim_Properties_UI_Complete_1.0.252_NoBundledRuntimes.zip`
as a reviewable integration branch on top of the committed 1.0.248 merge-prep
work and every intended change currently present in the primary worktree.

Merge-ready means the candidate's architecture, features, UI, tests, assets,
and packaging are retained or explicitly adapted; the existing uncommitted
regressions survive; project ownership contracts remain coherent; and current
package and Blender runtime evidence supports the result.

## Integration Strategy

Use a semantic three-way integration in an isolated worktree.

1. Reconstruct the uncommitted delta from its binary patch and untracked test.
2. Remove only accidental merge artifacts and duplicate definitions that make
   the current `sim/frame_output.py` syntactically invalid.
3. Prove the intended dirty-state regressions, then commit the clean semantic
   baseline separately.
4. Import the complete 1.0.252 candidate into the add-on package as a distinct
   provenance commit. Keep candidate-only development and release material
   available for assessment while respecting manifest exclusions.
5. Resolve overlapping files by three-way intent, preserving both the
   pre-existing fixes and compatible candidate behavior.
6. Commit compatibility corrections and product hardening separately from the
   candidate import.

The primary dirty worktree is not modified, reset, stashed, cleaned, or used as
an integration surface. A reconstruction backup is stored outside the repo at
`C:\tmp\fluidsim-1.0.252-preintegration-dirty-20260819T0825.zip`.

## Architecture

The target ownership map remains authoritative:

- `blender/simulation_admission.py` owns admission snapshots, preflight,
  replacement cutover, solver configuration, and admission cleanup.
- `blender/scene_bridge.py` owns the solver session and direct scene stepping.
- `blender/output_publication.py` owns persistent output publication.
- `blender/playback.py` owns preview and cache-playback policy.
- `blender/cache_bake.py` owns sequential production cache bake.
- `blender/pending_settings.py` owns setting lifecycle and pending state.

The 1.0.252 Scene Properties, Object Properties, cache-state, Custom Effects,
and Warp Code modules are adapters over those owners. They must not recreate
solver, bake, playback, publication, or pending-setting state machines.

The legacy panels are reduced to a compact launcher/status surface. Authored
simulation, source, cache, effects, diagnostics, and advanced settings live in
the appropriate Scene or Object Properties panels. Destructive cache actions
must remain fail-closed and revalidate their exact target at execution time.

## Dirty-State Carry-Forward

Every intended behavior in the uncommitted delta is retained, including:

- scene ownership checks before solver reuse;
- cache frames being consumed only after successful publication;
- correct empty and absent cache metadata handling;
- contiguous export and frame-output arrays;
- cached live counts for lazily requested particle and whitewater outputs;
- complete surface-attribute invalidation;
- safe capacity-growth arithmetic;
- robust authored-quality and source-sampling recovery;
- duplicate kernel-registration rejection;
- diagnostic correctness for zero baselines and profiling phase names;
- the associated root regression tests and the untracked core regression file.

Conflict markers, repeated `_live_count` definitions, and duplicated merge
fragments are not product behavior and are removed while preserving the tested
intent on both sides.

## Compatibility and Packaging

- Preserve the target's Blender 5.1 product contract unless executable evidence
  shows a 1.0.252 feature requires Blender 5.2.
- Treat Warp 1.16.0+cu12 as an external runtime; do not bundle Blender, Warp,
  CUDA, or platform runtimes into the add-on.
- Reconcile manifest, runtime version, package root, extension ID, exclusions,
  licenses, examples, and release metadata.
- Do not convert the candidate's Linux x64 validation claim into a Windows
  certification claim. Windows support is reported only to the level proved by
  current Windows package and Blender gates.
- Verify the built artifact rather than inferring package correctness from the
  source tree.

## Verification

Run the narrowest checks after each phase, then broaden:

1. parse/import and conflict-marker scans;
2. dirty-state regression tests and candidate unit tests;
3. ownership-specific project suites for playback, cache, output, admission,
   pending settings, source lifecycle, effects, surface tension, and UI;
4. full `python -m pytest -q`;
5. extension/package build and archive-content validation without runtimes;
6. Blender 5.1 background registration and focused acceptance gates;
7. demo inventory and real saved-demo playback checks;
8. `python tools/run_production_gate.py`, followed by the GUI-inclusive gate
   when the headless and packaging layers are stable;
9. in the surviving Blender process, prove the intended add-on is installed or
   intentionally loaded, enabled, registered from the expected path, and able
   to perform a minimal runtime round trip.

GPU nondeterminism is evaluated through physical, lifecycle, schema, and
bounded-error invariants rather than bitwise equality.

## Commit and Review Shape

The intended review sequence is:

1. this approved design;
2. clean semantic preservation of the pending uncommitted regressions;
3. faithful 1.0.252 candidate import;
4. architecture and compatibility corrections;
5. focused regression or product hardening commits;
6. current evidence and merge-readiness report.

No temporary extraction, cache, profile, build, or runtime files are committed.
The branch is complete only when current status, diff, history, packaging, and
runtime evidence support the claimed scope and all known residual risks are
reported.
