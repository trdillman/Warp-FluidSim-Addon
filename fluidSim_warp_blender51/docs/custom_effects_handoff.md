## Non-regression rules

- Never treat module import as Warp compilation success.
- Never omit an invalid enabled effect.
- Failed Test/Apply leaves the previous applied stack untouched.
- Runtime failure latches the manager failed and stops subsequent execution.
- Trust is exact-content SHA-256, not `built_in=True`, package metadata, filename, or effect ID.
- User packages cannot shadow built-in IDs.
- Cache/resume uses freshly recomputed effective Text/controller state at every boundary.
- Mute/solo filtering is shared by compiler, runtime, policy, and fingerprinting.
- Duplicate instance IDs fail closed.
- Legacy cache playback remains available; resume with active effects requires matching identity.
- Legacy snippet entry points remain adapters only for one migration release.

## Examples and validation

The three Custom Effects scenes under `resources/examples/` are static validation/review examples, not playable demos. They are generated by `../tools/release/generate_custom_effect_demos.py` and validated by `../tools/release/validate_custom_effects_blender.py`; numerical execution is in `../tools/release/custom_effect_demo_runtime.py`. They contain precomputed evidence and do not contain a live Domain-backed solver advancing through Blender frame handlers. Regenerate them whenever a behavior-affecting fingerprint rule changes, but do not use them as demo-playback evidence. A real Custom Effects demo must satisfy the repository's `docs/DEMO_SCENE_CONTRACT.md` and prove effect execution in a non-empty live solver.

CUDA remains a required external release-tag gate. Do not infer CUDA correctness from CPU Warp compilation/execution.
